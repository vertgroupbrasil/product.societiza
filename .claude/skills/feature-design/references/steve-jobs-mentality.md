# Mentalidade Steve Jobs — Guia de Pensamento de Produto

## Aviso de uso

Este documento não é uma biografia. Não é uma lista de frases motivacionais. É
um guia de raciocínio para quem está tomando decisões de produto. Leia antes de
propor qualquer feature, corte de escopo, ou mudança de direção. Se você não
consegue defender sua ideia à luz deste guia, provavelmente ela não está pronta.

---

## 1. O produto é a experiência, não o software

Steve Jobs não pensava em features. Ele pensava em experiências. A pergunta que
ele fazia não era "o que esse software faz?" mas sim "o que o usuário sente
quando usa isso?"

Isso muda tudo. Quando você pensa em features, você pensa em caixas de
funcionalidade que somam umas às outras. Quando você pensa em experiência, você
percebe que mais caixas muitas vezes pioram a experiência — porque adicionam
fricção, confusão, sobrecarga cognitiva.

Para a Societiza: o contador que abre o board pela manhã deve sentir imediato
controle e clareza. Não deve sentir que precisa aprender. Não deve sentir que
está navegando por um software complexo. Deve sentir que a operação está ali,
na frente dele, clara, pronta para ser tocada.

Toda decisão de produto precisa ser testada contra esse critério: isso aumenta
o senso de controle e clareza, ou aumenta o ruído?

---

## 2. Produto primeiro. Engenharia depois.

Um dos erros mais comuns em times de tecnologia é deixar a engenharia guiar o
produto. Quando a engenharia guia o produto, o resultado é features que existem
porque eram fáceis de implementar, não porque o usuário precisava delas.

Jobs tinha a ordem invertida. Ele definia a experiência que queria criar. Definia
o que o usuário deveria sentir. Definia o que era simples e bonito. Depois
entregava para a engenharia descobrir como fazer aquilo acontecer.

Isso não é ignorância técnica. É clareza de prioridade. Engenheiros brilhantes
são capazes de construir coisas extraordinárias quando o objetivo está claro.
O que os desorienta é quando o objetivo muda de "criar a melhor experiência
possível" para "implementar o que é tecnicamente mais conveniente agora."

Para a Societiza: quando você está definindo uma feature, a pergunta não é
"como implementamos isso?" A pergunta é "como deve ser a experiência?" Depois
que essa resposta está clara, a implementação é um problema de engenharia.

---

## 3. Simplicidade não é ausência de complexidade. É maestria sobre ela.

Jobs dizia que simplicidade é a sofisticação suprema. Isso é frequentemente mal
interpretado como "faça coisas simples e preguiçosas." Não é isso.

Simplicidade é o resultado de eliminar tudo que não é essencial até que o que
sobra seja exatamente o que precisa estar ali. Isso exige mais trabalho, não
menos. Exige mais decisões difíceis. Exige mais coragem para dizer não.

Um produto simples é aquele onde o usuário nunca fica em dúvida sobre o que
fazer. Onde a interface guia sem precisar explicar. Onde cada elemento tem um
propósito claro.

Um produto complexo é aquele onde o usuário precisa aprender antes de usar.
Onde o manual precisa existir. Onde o suporte técnico trabalha para explicar
o que o produto deveria tornar óbvio.

Para a Societiza: cada vez que você adiciona uma opção de configuração, uma
modal, um campo, uma coluna, uma tab — você está tornando o produto mais
complexo. Isso não é necessariamente errado. Mas é uma decisão que precisa ser
justificada. A pergunta é: "isso é necessário para que o usuário possa operar
melhor, ou estamos adicionando porque parece útil?"

---

## 4. O que você não constrói é tão importante quanto o que você constrói

Jobs era famoso por dizer não. Para features. Para produtos. Para ideias que
pareciam boas mas não eram essenciais.

Quando ele voltou para a Apple em 1997, a empresa tinha dezenas de produtos.
Ele cortou para quatro. Quatro produtos. A empresa quase faliu — e ele cortou
para quatro produtos. Essa decisão é frequentemente citada como uma das mais
importantes da história da Apple.

Dizer não não é fraqueza ou falta de visão. É uma forma de proteção. É garantir
que o time tenha foco suficiente para fazer poucas coisas extraordinariamente
bem, em vez de muitas coisas de forma medíocre.

Para a Societiza: uma feature que você não constrói agora não é uma feature
perdida. É uma feature que não vai distrair o usuário, não vai demandar
manutenção, não vai criar dívida de produto. Só construa quando você tiver
certeza de que o custo de não ter essa feature é maior do que o custo de tê-la.

---

## 5. Coerência de produto: cada peça fortalece o todo

Um dos maiores insights de Jobs sobre design de produto era que um produto não
é a soma das suas features. É o resultado da interação entre elas.

Features que parecem independentes interagem com todas as outras. Elas criam
padrões de uso. Criam expectativas. Criam modelos mentais. Quando você adiciona
uma feature que não se encaixa na experiência geral, você está fragmentando o
modelo mental do usuário.

Isso tem uma implicação prática: antes de adicionar uma feature, pergunte como
ela conversa com as features existentes. Não apenas tecnicamente, mas
experiencialmente. O usuário que usa X vai naturalmente querer Y? Y leva o
usuário de volta para X de forma que faz sentido?

Para a Societiza: o dashboard não existe para ser uma tela separada de
analytics. Ele existe para amplificar o societário. Cada número que o usuário
vê no dashboard deve poder virar uma ação no societário. Notificações não existem
para criar um módulo de mensagens. Existem para guiar o contador de volta ao
processo que precisa de atenção. Coerência não é visual. É funcional.

---

## 6. Protótipos mentais: sinta antes de construir

Jobs não esperava o produto ficar pronto para saber se era bom. Ele construía
protótipos mentais. Ele simulava a experiência na sua cabeça antes de qualquer
linha de código ou qualquer mockup.

Você pode fazer o mesmo. Antes de aprovar uma feature, simule o uso real:

- Como o usuário descobre essa feature?
- O que ele vai tentar fazer primeiro?
- Onde ele vai travar?
- Como ele vai saber que completou a tarefa?
- Como ele vai se sentir após usar?

Se você não consegue simular essa jornada de forma fluida na sua cabeça, a
feature não está definida o suficiente para ser construída.

Para a Societiza: antes de aprovar qualquer feature de produto, simule o uso
de um contador típico — sobrecarregado, com 30 processos abertos, sem tempo
para aprender — usando essa feature pela primeira vez. Se ele travar em
qualquer ponto da simulação, a feature precisa ser repensada.

---

## 7. Não pergunte ao usuário o que ele quer. Entenda o que ele precisa.

Henry Ford disse que se tivesse perguntado às pessoas o que queriam, elas teriam
dito "cavalos mais rápidos." Jobs acreditava no mesmo princípio.

Usuários são ótimos para descrever problemas. São péssimos para propor soluções.
Quando um usuário diz "quero um relatório em PDF", o que ele realmente quer é
ter evidência do trabalho feito para apresentar ao cliente. O PDF é uma solução
que ele imaginou. O problema real pode ter soluções muito melhores.

Isso não significa ignorar feedback. Significa interpretar o feedback no nível
correto. O que o usuário está realmente tentando fazer? Qual dor está tentando
eliminar? Qual insegurança está tentando resolver?

Para a Societiza: quando um contador pede "um jeito de ver quantos processos
estão atrasados", o problema real não é uma lista de processos atrasados. O
problema real é a ansiedade de não saber se há algo crítico sendo negligenciado.
A solução pode ser um número no topo do board, um badge, uma cor, um alerta —
não necessariamente uma tela nova de relatório.

---

## 8. Qualidade não é negociável. Nunca.

Jobs era infame por seu padrão de qualidade. Ele mandava refazer produtos que
para qualquer outra pessoa seriam considerados prontos. Ele se preocupava com
partes do produto que o usuário nunca veria — o interior dos computadores, o
layout das placas de circuito — porque para ele a qualidade era uma postura,
não uma métrica.

Isso não significa perfeccionismo paralisante. Significa que quando algo não
está certo, você não deixa passar. Quando uma interface parece errada, você
investiga por que. Quando um fluxo cria fricção, você resolve em vez de
aceitar como "bom o suficiente."

"Bom o suficiente" é o início do declínio de um produto.

Para a Societiza: um processo que trava em uma etapa sem feedback claro para o
contador não é "um bug menor." É uma falha de produto. Um campo que tem um label
confuso não é "detalhe de UX." É uma barreira para o usuário. Qualidade de
produto não é sobre perfeição visual. É sobre não aceitar fricção que você tem
poder de remover.

---

## 9. O lançamento certo > o lançamento rápido

Jobs nunca lançou um produto porque ele estava "pronto o suficiente." Ele lançou
quando a experiência estava certa. O iPhone não lançou com 3G, não lançou com
copy-paste, não lançou com a App Store. Lançou com uma experiência de telefone
e música e internet que era a melhor do mundo dentro daquelas três coisas.

Isso é uma escolha de produto deliberada. Fazer menos e fazer extraordinariamente
bem é sempre superior a fazer mais e fazer de forma medíocre.

Existe um equilíbrio aqui. Esperar muito tem custos reais: o produto não chega
ao usuário, o feedback não acontece, o mercado não valida. Mas lançar cedo
demais tem custos maiores: a primeira impressão é a mais duradoura, e um produto
ruim no primeiro contato cria uma rejeição difícil de reverter.

Para a Societiza: quando o societário lançar para um novo usuário, ele precisa
criar uma primeira impressão de clareza, controle e alivio. Se o primeiro
contato criar confusão ou frustração, esse usuário carrega essa impressão para
sempre. Priorize a experiência da primeira jornada de uso acima de qualquer
lista de features.

---

## 10. Custo de produto é parte da decisão de produto

Jobs pensava em produtos de forma holística. Isso incluía custo. Não apenas
custo de desenvolvimento, mas custo estrutural de manutenção, custo de suporte,
custo de complexidade cognitiva para o usuário, e quando relevante, custo de
serviços externos.

Uma feature que exige integração com uma API paga tem um custo recorrente que
precisa estar na decisão de produto. Não apenas no plano financeiro. Na decisão
de produto: esse valor que criamos para o usuário justifica esse custo? Podemos
passar esse custo para o usuário? É parte de um tier mais alto do produto?

Custo não é responsabilidade exclusiva da engenharia ou do financeiro. É parte
da decisão de produto.

Para a Societiza: se uma feature de notificações exige um provider de WhatsApp
(ex: Twilio, Zenvia, Z-API), isso é uma decisão de produto. O contador vai
pagar mais por isso? Entra em qual plano? Tem um volume mínimo que justifica o
custo de integração? Essas perguntas precisam estar respondidas antes da feature
ir para engenharia.

---

## 11. A jornada importa tanto quanto o destino

Jobs se importava com cada detalhe da jornada do usuário. Não apenas com o
resultado final. A embalagem do iPhone era projetada para que a experiência de
abrir a caixa fosse memorável. O som do clique do botão Home era calibrado para
dar prazer. O caminho de configuração inicial era projetado para ser excitante.

Isso se aplica diretamente ao design de produto: a jornada do usuário — o
caminho que ele percorre para chegar ao valor — precisa ser boa em cada ponto.
Onboarding ruim mata produtos. Loading states mal pensados criam ansiedade.
Mensagens de erro genéricas frustram. Cada passo entre o usuário e o valor
é uma oportunidade de fortalecer ou destruir a confiança dele no produto.

Para a Societiza: a jornada de um contador desde "preciso abrir uma empresa
para o meu cliente" até "processo concluído e empresa aberta" tem dezenas de
pontos de contato com o produto. Cada um importa. A criação do processo. A
visualização das tarefas. O drawer de detalhes. O feedback de progresso. A
conclusão de uma etapa. Nenhum desses momentos pode ser descuidado.

---

## 12. Produto para pessoas reais em situações reais

Jobs tinha um talento especial para imaginar o usuário em contexto real. Não
o usuário em um laboratório de usabilidade. Não o usuário com tempo ilimitado
e paciência infinita. O usuário real — apressado, sobrecarregado, distante,
usando o produto em 30 segundos entre uma reunião e outra.

Quando você pensa em uma feature, pense em quem vai usar, onde vai usar, quando
vai usar, com que nível de atenção vai usar. Um contador usando o board no
celular enquanto espera um cliente não tem a mesma capacidade de atenção que um
counter usando no desktop no início do dia.

Para a Societiza: o ICP é um escritório de contabilidade pequeno ou médio, com
uma equipe enxuta, provavelmente com sobrecarga de trabalho, provavelmente
usando o produto em múltiplos contextos ao longo do dia. Qualquer feature que
exige treinamento, qualquer interface que exige aprender uma nova lógica, tem
um custo de adoção alto demais para esse perfil de usuário.

---

## 13. Não construa features. Resolva problemas.

Existe uma diferença fundamental entre pensar em features e pensar em problemas.

Features são soluções sem problema definido. "Vamos adicionar um histórico de
atividades." Por quê? Para quê? Quem precisa? Em que situação isso é necessário?

Problemas são o ponto de partida correto. "O contador perde tempo tendo que
ligar para o cliente para saber se ele já enviou os documentos." Agora você
tem um problema real. A solução pode ser uma notificação, pode ser um portal,
pode ser um status visível no card, pode ser outra coisa. Mas o problema guia
a decisão.

Para a Societiza: antes de propor qualquer feature, defina o problema. Quem
tem esse problema? Com que frequência? Qual o impacto? O que eles fazem hoje
para contornar? Sem um problema claro, uma feature é apenas ruído no produto.

---

## 14. Integridade do produto ao longo do tempo

Jobs pensava no produto em múltiplos horizontes de tempo. Não apenas o que
lança hoje, mas o que o produto se torna em 3 anos, em 5 anos. Cada decisão
de hoje afeta as decisões de amanhã.

Uma feature mal projetada hoje cria dívida de produto. Cria expectativas nos
usuários que são difíceis de reverter. Cria padrões de interface que se
propagam. Cria código que precisa ser mantido e eventualmente substituído.

Por isso decisões de produto precisam considerar não apenas o valor imediato
que entregam, mas o tipo de produto que elas estão construindo a longo prazo.

Para a Societiza: cada feature que lança deve ser consistente com a visão de
longo prazo do produto como sistema operacional da abertura de empresas. Não
como um conjunto de ferramentas. Como um sistema coeso. Isso significa que
features de diferentes momentos do roadmap precisam parecer que foram projetadas
juntas — não empilhadas umas sobre as outras.

---

## 15. Perguntas obrigatórias antes de aprovar qualquer feature

Antes de considerar uma feature aprovada para desenvolvimento, responda:

1. Que problema específico e real essa feature resolve?
2. Para quem exatamente? Em qual momento da jornada?
3. Como o usuário resolve esse problema hoje sem a feature?
4. O que você vai remover ou simplificar para acomodar essa feature?
5. Como essa feature conversa com o que já existe no produto?
6. O que essa feature abre para o futuro?
7. O que essa feature pode fechar ou complicar no futuro?
8. Se você pudesse lançar a metade dessa feature, qual metade seria?
9. Existe um custo externo (serviço, API, infraestrutura) para essa feature?
10. Como o usuário descobre essa feature sem ser ensinado?

Se você não tem resposta clara para pelo menos 8 dessas 10 perguntas, a feature
não está pronta para ser aprovada.

## 16. O que Jobs pensaria sobre a Societiza

Pensando na Societiza através da lente de Jobs:

**O que ele diria que está certo:**
- O kanban como centro operacional é a decisão certa — visual, imediato, acionável.
- Templates configuráveis são a decisão certa — dão ao usuário o poder de adaptar sem exigir desenvolvimento.
- Focar no contador como usuário primário é a decisão certa — serve quem tem a dor real, não quem é o beneficiário final.

**O que ele provavelmente questionaria:**
- Por que o usuário precisa navegar em múltiplos lugares para fazer uma coisa só?
- O onboarding está preparado para um contador que nunca usou software de workflow?
- O que acontece quando um contador passa dois dias sem abrir o sistema e volta — ele sabe imediatamente o que precisa de atenção?
- Existe uma experiência de "uau, isso me deu controle" no primeiro uso?

**O que ele diria sobre o roadmap:**
- Dashboard antes de notificações: certo. Você precisa dar ao usuário visibilidade antes de poder alertá-lo sobre o que ele vê.
- Portal do cliente depois de notificações: certo. O cliente só precisa de acesso quando há algo para ver.
- Formulário nativo antes de alvarás: incerto. Depende de qual dor é maior para o ICP hoje.

---

## 17. Resumo executivo

Se você vai lembrar apenas de uma coisa deste documento:

**Produto é o que o usuário sente. Engenharia é como você faz ele sentir isso.**

Comece sempre pelo sentimento que você quer criar. Depois construa o caminho
para chegar lá. Nunca ao contrário.

E quando estiver em dúvida sobre incluir ou não uma feature: não inclua.
O produto sempre fica melhor quando você remove do que quando você adiciona.

A simplicidade é o resultado de decisões corajosas de produto. E coragem, nesse
contexto, significa ter convicção suficiente para dizer não quando todos ao redor
estão dizendo sim.
